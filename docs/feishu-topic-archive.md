# Feishu topic archives

With `turn_record_mode = "topic"`, one local conversation within an explicit Feishu topic owns one Bitable main record. Follow-up turns update that record. `/new` starts a separate record; provider resets and service restarts preserve the record identity. Messages outside a topic remain independent records.

The main record keeps the original question and requester, the latest answer and Trace link, every delivered question and answer, and all per-turn Trace links. Turn count, elapsed processing time and tool calls are accumulated from unique completed turns. Time between user messages is excluded; time waiting for clarification inside a running turn is included. A steered message remains part of its original turn, with its sender and question text retained. Accepted native clarification questions and selections are also retained within that turn; expired, rejected and duplicate submissions are excluded.

Elapsed duration remains the wall-clock time from beginning execution to delivering the final answer. User wait is measured separately, from successful delivery of an actionable clarification or approval request until the valid response arrives. The interval is committed only after the agent accepts that response. Each question in a multi-question request is timed separately, excluding delivery gaps and response submission time. Automatic approval, queue time and idle time between turns are excluded from user wait. Failed submissions remain pending; duplicate and expired responses do not change timing. Steers retain the current turn's clock, while queued turns start a new one.

The optional numeric mappings `active_duration`, `user_wait_duration`, `timed_turn_count`, `slow_turn_count`, `mean_turn_duration` and `slow_turn_ratio` must be configured together. A valid timed round has positive elapsed duration and a measured or reconstructed user-wait interval between zero and elapsed duration. Net processing time is elapsed minus user wait. `active_duration` and `user_wait_duration` accumulate valid samples; `timed_turn_count` counts those samples; `slow_turn_count` counts rounds whose net time exceeds 300 seconds. Per-record mean and slow ratio are null when no valid samples exist. Overall dashboard metrics divide the sum of net durations or slow rounds by the sum of valid round counts; they never average per-topic averages. The original elapsed total remains available in task details.

Historical wait times may be reconstructed only from complete, bound request/response events or complete evidence that no human pause occurred. Missing or ambiguous evidence stays unknown and is excluded from net-time statistics. The canonical journal retains the original elapsed duration and records whether wait timing was measured or reconstructed. Snapshot historical state before modifying it, preserve new measured rounds, and report timing coverage alongside the statistics.

The configured text columns `task_id`, `conversation`, `trace_history`, `archive_state`, and `record_kind`, plus numeric `turn_count`, are required. Existing field mappings retain their types. `archive_state` contains the versioned canonical per-turn journal; hide it and `task_id` from normal views, but retain them for recovery. Filter the main view and dashboard to exclude `record_kind = 历史明细`, allowing any legacy records to remain visible during a rollback.

One recorder worker serializes updates. Each write first reads the existing task record; native session/turn IDs (or the triggering message ID) identify retries. An identical retry does not add a turn or accumulate metrics. Conflicting retries, duplicate task rows, invalid state, unexpected field types, and text exceeding 100,000 bytes fail without overwriting existing history. Multiple service instances must not write to the same topic concurrently. Recording is best effort and does not fail or replay the user's task.

Historical consolidation requires verified Trace-to-turn and persisted local-session mappings. Snapshot source records before applying changes. Update the first record in each confirmed task with the canonical journal and aggregates; mark the other source records `历史明细` and leave their task IDs empty. Keep unmapped records separate. No source rows are deleted. Validate stored round counts, transcript contents, Trace links, totals and unique task IDs before enabling topic mode.

Regression coverage must include multi-turn aggregation, independent topics and `/new`, native resets/restarts, queued and steered messages, identical and conflicting retries, uncertain write outcomes, invalid state and size limits. Timing coverage includes multiple prompts, failed or duplicate answers, cancellation, zero or unknown samples, unequal topic lengths and the five-minute boundary. Deployment preserves the native clarification and notification settings and verifies service health and stored records after switching.
